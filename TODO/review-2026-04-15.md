# Review complète — ProjetTicket
_Date : 2026-04-15_

## CRITIQUE

### 1. `@Roles()` est du code mort — RolesGuard jamais appliqué

`RolesGuard` est déclaré dans `providers` de `auth.module.ts` (ligne 34) mais **jamais enregistré globalement** (pas de `APP_GUARD`) et **jamais utilisé dans un `@UseGuards()`** sur aucun controller.

Résultat concret :
- `DELETE /messages/:id` (`@Roles('admin')`) → accessible à tout utilisateur authentifié
- `DELETE /piece-jointes/:id` → idem
- `POST/PATCH/DELETE /categories` → tout utilisateur peut créer/modifier/supprimer des catégories
- `POST/PATCH/DELETE /equipes` → idem
- **CRUD complet `/roles`** → tout utilisateur peut créer ou modifier des rôles
- `GET/POST/DELETE /utilisateurs` → tout utilisateur peut lister tous les comptes, créer et supprimer des utilisateurs
- `POST /historique-actions` → tout utilisateur peut injecter de faux historiques

> Les routes **tickets** sont protégées en pratique car `TicketsService`/`AccessService` font les vérifications métier en service. Mais tout le reste ne l'est pas.

**Fix :** enregistrer `RolesGuard` globalement dans `AppModule` :
```ts
providers: [{ provide: APP_GUARD, useClass: RolesGuard }]
```
...et s'assurer que chaque module exporte ce qu'il faut, **ou** ajouter `@UseGuards(JwtAuthGuard, RolesGuard)` explicitement sur chaque controller qui s'appuie sur `@Roles()`.

## MOYEN

### 2. `id_ticket` non validé dans `piece-jointes.controller.ts` (ligne 28)

```ts
const id_ticket = (req as any).body.id_ticket
```
Le champ `id_ticket` vient du multipart form-data, hors portée du `ValidationPipe`. Il n'est pas vérifié (`IsUUID`, `IsNotEmpty`). Un `id_ticket` vide ou invalide passe au service, qui lève une erreur Prisma non contrôlée plutôt qu'une `BadRequestException` lisible.

---

### 3. `DELETE /messages` et `DELETE /piece-jointes` — pas de vérification en service

`messages.service.ts` (ligne 106) et `piece-jointes.service.ts` (ligne 74) : les méthodes `remove()` ne font aucun contrôle d'accès. Une fois le point 1 corrigé, le guard vérifie le rôle mais personne ne vérifie que la ressource existe avant de supprimer (erreur Prisma brute P2025 au lieu d'un 404 propre si l'ID est inconnu).

---

### 4. `useTicketDetail` — crash Promise.all si l'utilisateur n'est pas admin

`frontend/src/hooks/useTicketDetail.ts` (lignes 25-33) :
```ts
Promise.all([fetchTicket(id), fetchUtilisateurs()])
```
`fetchUtilisateurs()` appelle `GET /utilisateurs`, protégé `admin`. Une fois le point 1 corrigé (RolesGuard actif), tout utilisateur non-admin qui ouvre un ticket verra une erreur et **le ticket ne s'affichera pas**.

**Fix :** conditionner l'appel selon le rôle, ou déplacer ce fetch dans le composant d'assignation (visible uniquement pour les managers).

---

### 5. `TicketDetailPage` — PATCH déclenché à chaque `onChange`

`frontend/src/pages/TicketDetailPage.tsx` (lignes 38-43) : le select "État" et le select "Agent assigné" appellent `handleUpdate` directement dans `onChange`. Scroller les options déclenche un appel API pour chaque valeur survolée.

**Fix :** état local intermédiaire + bouton "Sauvegarder", ou au minimum un debounce.

---

### 6. `useCreateTicket` — ticket orphelin si `createMessage` échoue

`frontend/src/hooks/useCreateTicket.ts` (lignes 32-47) :
```ts
const ticket = await createTicket(...)   // crée le ticket en base
await createMessage(...)                 // si ça échoue ici →
```
Le ticket est créé, l'erreur s'affiche, mais le ticket reste en base sans description. L'utilisateur peut retenter et créer un doublon.

**Fix :** traiter la description comme un message optionnel (créé après navigation), ou gérer une transaction côté backend.

---

### 7. `GET /historique-actions` — aucun filtre d'accès

`backend/src/historique-actions/historique-actions.controller.ts` (ligne 22) : `findAll()` retourne **tout l'historique de toutes les actions** sans restriction par équipe ni ticket. Un manager ou agent peut voir des historiques qui ne lui appartiennent pas.

---

### 8. `UtilisateursPage` — route accessible directement par URL

`frontend/src/App.tsx` (ligne 29) : la route `/utilisateurs` est dans `ProtectedRoute` (user connecté) mais sans garde de rôle. Tout utilisateur connecté peut y accéder via l'URL directe, même si le menu ne la montre qu'aux admins.
